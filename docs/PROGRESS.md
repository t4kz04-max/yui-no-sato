## Phase 3 の設計（技術的な判断と理由）

1. **計画は「項目の組み合わせ」**：P1〜P3 という名前付きの正解を選ばせず、日取り・頼み方・申し出を組み合わせる。代表的な組み合わせが P1〜P3 に当たる。
2. **返事は純粋関数**（`PLANNING.respond`）：入力は案の内容だけ。過去の貸し借り・会話の回数・好感度・情報の有無は入力にしない（テストで確認）。プレイヤーが知っているかどうかで変わるのは「返事の理由を説明してもらえるか」と「案の選択肢が思いつけるか」だけ。
3. **返事は案ごとに記録**：案を変えたら古い承諾で決定できない。決定の判定は今の案への返事だけで行う。
4. **情報で選択肢を出す／隠す**：未取得の情報を前提とした案は出さない（PHASE_PLAN §8 の条件を先取りして守る）。ただし「予定日・伊助に頼まない」は常に選べるので、進行不能にならない。
5. **正解を一つにしない**：早さ・伊助が関われるか・新しい負担・屋根の傷み・残る約束が互いに引き換え（`docs/VERTICAL_SLICE.md` §1）。
6. **会話データに条件分岐（branches）を追加**：相談の返事の理由に応じて反応の台詞へ進む。会話データの検証も分岐に対応。
7. **結帳の返しの状態を 3 値に**：返しまだ／返し済／取り決めなし。刈り入れの手伝いと屋根の手伝いを「釣り合い」で相殺したことにしない。
8. **既存の仕組みを拡張**：状態（StoryState）・条件・会話・イベント・保存・画面の遷移を拡張し、作り直していない。新しい依存ライブラリはなし。

### 技術的な判断

1. **全面破棄ではなく「移植＋再構成」**：見た目の構築コードは移植し、設計書 N 節で再設計対象とされた移動・当たり判定・カメラ・構造を作り直した。
2. **当たり判定は XZ 平面の 2D（回転矩形＋円）**：ジャンプのない探索ゲームのため 3D 物理エンジンは不要。描画と同じ配置データ（`world/layout.ts`）から生成し、見た目と判定のずれを防ぐ。
3. **状態と描画の分離**：`PlayerController`（純粋ロジック）→ `PlayerView`（見た目に反映するだけ）。カメラも `orbit.ts`（純粋計算）と `ThirdPersonCamera`（Three.js）に分離。
4. **移動はフレームレート非依存**：加速を解析的に積分し、30fps と 144fps で移動距離が一致する。dt は最大 0.1 秒に制限。
5. **視点操作はマウスドラッグ方式**：ポインターロックは会話・手帳 UI のクリック操作と衝突しやすいため見送り。
6. **描画負荷の削減（計測に基づく）**：初版の約 1,170 回の描画呼び出しを、木の InstancedMesh 化と静的メッシュの結合で約 96 回に削減。
7. **影は村全体を覆う固定範囲**（2048px）。
8. **Tailwind は不採用**。
9. **入力の抽象化**：ゲームはキーコードを直接見ず `MoveIntent`／`OrbitInput` を受け取る。
10. **座標系**：北 = -Z、南 = +Z、東 = +X、西 = -X。スタートは橋の南（0, 31）で北を向く。

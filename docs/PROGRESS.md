## Decisions（技術的な判断と理由）

1. **全面破棄ではなく「移植＋再構成」**：見た目の構築コード（建物・地形・光・小物・人物）は移植し、設計書 N 節で再設計対象とされた移動・当たり判定・カメラ・構造を作り直した。
2. **当たり判定は XZ 平面の 2D（回転矩形＋円）**：ジャンプのない探索ゲームのため 3D 物理エンジンは不要。純粋関数でテスト可能。描画と同じ配置データ（`world/layout.ts`）から生成し、見た目と判定のずれを防ぐ。
3. **状態と描画の分離**：`PlayerController`（純粋ロジック、Three.js 非依存）→ `PlayerView`（見た目に反映するだけ）。カメラも `orbit.ts`（純粋計算）と `ThirdPersonCamera`（Three.js）に分離。
4. **移動はフレームレート非依存**：加速を指数関数で解析的に積分し、30fps と 144fps で移動距離が一致する（テストで確認）。1フレームの dt は最大 0.1 秒に制限し、タブ復帰時のすり抜けを防ぐ。
5. **視点操作はマウスドラッグ方式**：ポインターロックは Phase 1 以降の会話・手帳 UI のクリック操作と衝突しやすいため見送り。必要なら Phase 6 の操作性調整で再検討。
6. **描画負荷の削減（計測に基づく）**：初版は 1 フレーム約 1,170 回の描画呼び出しだったため、木を InstancedMesh、建物の静的な部品をマテリアル単位で結合（`render/mergeStatic.ts`）し、**約 96 回**に削減。
7. **影は村全体を覆う固定範囲**（2048px）：プレイヤー追従は移動時に影がちらつくため。
8. **Tailwind は不採用**：CDN 版は本番向けでなく、現段階の UI は小さいため素の CSS で十分。
9. **入力の抽象化**：ゲームはキーコードを直接見ず `MoveIntent`／`OrbitInput` を受け取る。`InputManager.enabled` で移動・視点入力を止められる（Phase 1 の会話中の操作制御用の入口のみ用意）。
10. **座標系**：北 = -Z、南 = +Z、東 = +X、西 = -X。スタートは橋の南（0, 31）で北を向く。
11. **村の配置は仮**：5地点の位置関係は設計書 E 節に準拠。主要地点を歩いて一周約 1 分（徒歩 2 分以内の条件を満たす想定）。
12. **追加した依存**：`vitest`（自動テスト）、`puppeteer-core`（ブラウザ確認スクリプト用。ブラウザ本体は同梱せずローカルの Chrome を使う）。いずれも開発用のみ。`npm audit` は 0 件。

## Known Issues（既知の問題）

- 建物・人物・木はすべて仮モデル（Phase 5 で作り込み）。茅葺きの色むらや素材感はまだない。
- 近距離で建物に寄ると、カメラが非常に近くなり人物が画面を大きく占める（壁抜け防止の仕様上）。Phase 6 で人物の半透明化などを検討。
- 外周は見えない境界（歩行範囲の矩形）で止まる。山すそと森で自然に見えるよう配置しているが、境界に沿って歩くと不自然に感じる可能性がある。
- 合掌造りの玄関を妻側（棟の端）に配置しているのは試作を踏襲した仮配置。実在の家屋の入口の位置との整合は Phase 5 で資料を確認して決める。
- `npm run build` で JS チャンクが 500KB を超える旨の警告は出ない設定にしている（Three.js 本体が大半。必要なら Phase 8 で分割）。
- `npm run test:browser` はローカルの Chrome（既定パス）が必要。別の場所にある場合は `$env:CHROME_PATH` で指定する。

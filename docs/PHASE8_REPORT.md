## 4. ブラウザテスト異常の調査結果

### 異常A：橋の通行テストの失敗（`[P5.5] 橋の出口から入口まで歩いて渡れる（北→南）`、z=27.44）

- **期待：** z>28（橋の南端 z=26.2 の先）。**実際：** z=27.44 に達していて、橋は渡り終えていた。
- **テストの判定方法：** キーを押し続け、**実時間で 20 秒**以内に z>28 へ届くかを見ていた（`holdUntil(..., 20000)`）。
- **ゲームの時間の進み方：** 1 フレームで進む時間は最大 0.1 秒（`MAX_FRAME_DT`）。そのため描画が遅いと、ゲーム内の時間は実時間よりずっと遅く進む。
- **単独での再現（`browser-bridge.mjs`）：**
  - 両方向とも渡れた。
  - 渡るのにかかった時間は、ゲーム内 2.7〜3.0 秒、実時間 8〜12 秒（SwiftShader で 2.4〜3.6 fps）。
  - 欄干寄り（x=±0.9）を歩いても止まらなかった。
  - 0.5 秒（ゲーム内）以上動かない「引っかかり」はなかった。
- **失敗した回の状況：** 型チェック・ユニットテスト・ビルドを並行して実行した時間と重なっていた。実時間 20 秒で z=27.44 にとどまるのは、おおむね 1.5 fps を下回った場合に当たる。
- **結論：** 原因は、テストが実時間の制限で判定していたこと（描画の遅さへの耐性不足）。ゲームの当たり判定と移動処理の不具合ではない。
- **修正：**
  - フルテストの橋の 2 項目を、ゲーム内の時間（`window.__yui.clock`）で 8 秒まで待つ判定に変えた（`holdUntilGame`）。実時間の上限は、止まったとき用に 180 秒とした。
  - 回帰テスト `browser-bridge.mjs` を追加した（両方向・欄干寄り・引っかかりの検出・Chrome の CPU スロットリング 4 倍）。
  - なお、CPU スロットリングは SwiftShader の描画（GPU プロセス）には効かず、fps はほとんど下がらなかった。低 fps の再現は限定的である。

### 異常B：テスト用の Chrome の途中終了（「detached Frame」「Session closed」）

- **Windows のイベントログ（System）で確認した、PC のモダン スタンバイ：**
  - 15:09:46 にモダン スタンバイへ入った（Kernel-Power 506）。
  - 15:10:02〜15:10:48 にもう一度入った。
  - 15:12:33〜15:27:25 にもう一度入った。
- **2 回目のテストとの対応：** 15:11 ごろに開始し、カメラの回転の確認（14 項目目）の直後に止まった。15:27 にスタンバイが明けた直後、「Session closed」で終わった（ログの最終書き込みは 15:27）。
- **1 回目のテストとの対応：** 14:58 開始。「detached Frame」で終わった時刻も、15:09 のスタンバイと一致する。
- **そのほかの所見：** Application ログには Chrome のクラッシュ（Windows Error Reporting・Application Error）の記録がなかった。
- **結論：** 途中終了は、テストの実行中に PC がスタンバイに入ったことによる（環境の要因）。ゲームのコードとテストのコードの不具合ではない。
- **対処（テストの実行環境の側だけ。ゲームのコードは変更なし）：**
  - `scripts/test-env.mjs` を追加した。
    - `keepAwake`：テストの実行中だけ、Windows にスリープと画面オフをしないよう求める（SetThreadExecutionState）。テストが終われば元に戻り、電源設定は変えない。環境変数 `NO_KEEP_AWAKE` で無効にできる。
    - `watchClock`：実時間の飛び（PC の停止）を検出し、結果に記録する。
  - 各ブラウザテストを変更した。
    - 結果を 1 行ずつ出す（途中で止まっても、どこまで進んだか分かる）。
    - テスト用のブラウザとの接続が切れたら、**終了コード 1** で終える。
    - ページのクラッシュをエラーとして記録する。
    - 最後に合計と「PC が止まっていた形跡」を出す。
- **確認したこと：**
  - テスト用の Chrome（`browser-bridge.mjs` の子プロセス）だけを終了させると、「FAIL テスト用のブラウザが最後まで動く」と出て、終了コードは 1 になった。
  - 時刻の飛びの検出も、模擬で確かめた。
- **前回の報告の訂正：** 前回の「終了コード 0」という表示は、テストの後に実行した `echo` の終了コードだった（ログには `TEST_EXIT=1`）。今回は、テストのコマンドそのものの終了コードを記録している。

## 8. Vercel の設定の確認

`vercel.json`：

```json
{ "framework": "vite", "installCommand": "npm ci", "buildCommand": "npm run build", "outputDirectory": "dist" }
```

- **インストール：** `npm ci` は `package-lock.json`（lockfileVersion 3）どおりに入れる。Linux 用のネイティブのパッケージ（rolldown・typescript・lightningcss の linux-x64）も lockfile に入っている。
- **Node.js：**
  - Vite 8 の要件は `^20.19.0 || >=22.12.0`。Vercel の既定の Node.js（20.x 以降の LTS）なら満たす。
  - `package.json` に `engines` の指定はない。Vercel のプロジェクト設定の Node.js のバージョンは、作成者の画面で確認する（未確認）。
- **ルーティング：** ページは 1 枚（`index.html`）で、URL による画面の切り替えはない。書き換え（rewrites）の設定は不要。
- **キャッシュ：** JS と CSS のファイル名には内容のハッシュが付く（例：`index-0sSZCcxc.js`）。更新すると名前が変わるので、古いファイルが残る心配は小さい。`index.html` は Vercel の既定で毎回確かめ直す（未確認）。
- **HTTPS：** 外部の読み込み（http の混在）はない。
- **セーブデータ：**
  - ブラウザの `localStorage` に保存する（キー `yui-no-yakusoku:save:1`）。保存先は**オリジン（ドメイン）ごと**に分かれる。
  - Vercel のプレビュー用 URL と本番の URL、独自ドメインに変えた場合などでは、記録は引き継がれない。
